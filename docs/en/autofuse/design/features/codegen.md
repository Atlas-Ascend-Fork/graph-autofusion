# Codegen

## 1. Feature Background

### 1.1 Position of Codegen in the Autofuse Pipeline

The Autofuse compilation pipeline is: graph optimization (Optimize) → scheduling (Schedule) → code generation (Codegen) → performance tuning (ATT/Auto Tiling), where:

- **Schedule** makes splitting decisions on the fused computation graph (UB splitting, inter-core splitting, multiple templates) and outputs ImplGraph;
- **Codegen** parses ImplGraph and generates actual executable code, including code running on the Host side (Host Code) and the Device side (Kernel Code);
- **ATT** computes the concrete values of tiling (tiling_key, sizes of each split axis, etc.) before running, and fills them into the data structures generated by Codegen.

The core design philosophy of Codegen is: **Codegen only generates the "shape" of the code, not the "value" of tiling**. All splitting-related quantities in the code (tiling_key, axis sizes, loop counts) are placeholders in the form of tiling_data variables; the concrete values are computed by ATT on the Host side at runtime and passed in, so that the same generated code can adapt to different shapes and hardware resource conditions.

### 1.2 Design Goals

- **Schedule once, adapt everywhere**: Schedule generates multiple ImplGraph templates for different splitting strategies; Codegen generates all of them and dispatches by tiling_key, selecting the optimal template at runtime according to the actual shape;
- **Self-contained generated code**: The kernel source file inlines all dependent AscendC API source code, so it can be compiled independently;
- **Platform extensibility**: Through the ApiCall registration mechanism and the platform extension layer, Codegen supports operator integration of different computation categories (Vector/Cube/MicroAPI) and different SoC versions, while the main Kernel generation flow remains platform-independent.

## 2. User Scenarios

| Scenario | Description |
| --- | --- |
| Static shape fusion compilation | TF/ATC frontend integration; shapes are known at compile time. Codegen generates multi-template kernels with register-based tiling_key dispatch, with zero parsing overhead at runtime |
| Dynamic shape fusion compilation | Shapes are unknown at compile time; tiling is computed on the Host side at runtime. Codegen generates a dispatch structure that parses tiling_data at runtime |
| PyTorch Inductor integration | Generates Inductor-specific interfaces via the `GenerateForInductor` path, supporting full-const tiling hoisting for static shapes and TopN tiling candidate selection |
| CV (Cube/Vector) fusion | Matmul and other operators fused with Vector operators. Codegen generates multi-group CV kernels and the accompanying tiling wrapper |
| PGO tiling search | Generates a standalone tiling search executable that measures the performance of tiling candidates on real hardware and saves the best result for compile-time use |

## 3. Special Background and Limitations

This section describes the constraints on Codegen's cooperation with adjacent components. Most of these constraints cannot be directly derived from the code of a single module; they are implicit contracts of inter-module cooperation.

### 3.1 Contract with Schedule (ImplGraph)

ImplGraph is the only interface between Schedule and Codegen; Codegen makes no scheduling decisions. The implicit constraints include:

- **Axis completeness**: The axes on ImplGraph must form a complete splitting tree (ORIGINAL → TILE/BLOCK OUT/IN pairs). Codegen handles three categories: BLOCK_OUT (inter-core parallelism, no for loop), BLOCK_IN (generates in-core offsets), and all other axes (generates for loops). Missing pairs result in incomplete generated loop structures;
- **Node information completeness**: The repeats/strides/vectorized_strides of each node must be consistent with the axis dimensions, and the dtype combinations must be within the range supported by the API. Codegen validates them before generation (`CheckGraphValidity`) and terminates compilation directly on failure. The int64 dtype of Broadcast is currently exempted from validation;
- **Expression translatability**: The shape/offset expressions (`ge::Expression`) on the graph must be translatable into combinations of "tiling variables + loop variables". Codegen does not support expressions that cannot be evaluated at runtime; for example, expressions depending on Host-side randomness must not appear in axis definitions.

### 3.2 Responsibility Boundary with ATT/Auto Tiling

- **Codegen determines the structure, ATT determines the values**: The fields of `AutofuseTilingData` (which axes need size variables, tiling_key, block_dim) are determined by Codegen according to the splitting strategy, but the concrete values of the fields are computed by ATT. The definitions on both sides must be consistent; this consistency is guaranteed by both sides sharing the same TilingData generation code. Modifying fields on either side alone will cause misalignment at runtime;
- **Performance modeling is on the ATT side**: When assembling API parameters, Codegen computes information such as `outer_call_count` (the number of outer API calls) and writes it into node parameters. The performance formula of Auto Tiling (latency ≈ API call count × per-call latency) takes this as input for tiling candidate evaluation. The performance formula itself is not in Codegen; when Codegen adds new API parameters, it must confirm whether the formulas on the ATT side depend on them;
- **Fallback limits of PGO/TopN**: When the number of tiling_keys exceeds the upper limit (10000), the PGO search is automatically disabled and falls back to regular tiling generation; when the number of tiling_keys exceeds the limit of a single compilation unit, the kernel is automatically split into multiple compilation units for separate compilation. The two limits are different and take effect independently.

### 3.3 Dependency on the External Tiling Library

The actual generation logic of Host-side tiling functions resides in an external gen_tiling library. Codegen calls back to generate via a function pointer (`TilingLibCodegenFunc`, pointing to the `CodegenTiling` symbol in gen_tiling.so), and Codegen is responsible for assembling headers and concatenating translation units. This means:

- Changes to tiling code generation capability may involve synchronized updates of the gen_tiling library; the two must be released together;
- If the gen_tiling library is missing or the symbols do not match, tiling generation fails, which is an independent failure path from kernel generation.

### 3.4 Platform (SoC Version) Constraints

- Different SoC versions (e.g., 3510, 5102, 9201, 9202) differ in instruction sets and API forms. Version differences are routed to different implementations (V2 implementations) through the IR registry by SoC version; the main Codegen flow is unaware of the specific chip;
- Adding support for a new SoC version requires providing both the ApiCall implementations and the API source template registrations of that version; templates of other versions must not be reused;
- The AscendC API source code called in kernel files is packed into strings from source headers at build time and registered by `AscendCApiRegistry`, then inlined during generation. After an API template is updated, the Codegen module must be recompiled; otherwise the generation result still uses the old template.

### 3.5 Other Limitations

- **IO count limit**: When the number of inputs/outputs of a single fused operator exceeds 64, kernel parameters automatically switch to the list_tensor form; exceeding this limit may trigger compilation failure;
- **Queue depth and UB capacity**: UB memory allocation (queue depth, double buffer) is given by the mem/que information on ImplGraph; Codegen translates it faithfully without post-adjustment. Validation of UB overrun happens in the Schedule phase;
- **Tiling of Cube operators depends on the official implementation**: The tiling of Matmul/Conv calls the official matmul tiling interface (`AutofuseDoCubeMatMulTiling`) through a wrapper; Codegen does not implement Cube tiling algorithms itself.

## 5. Overall Architecture

Codegen provides a unified entry through the facade class `Codegen` (autofuse/codegen/codegen.h). A single generation produces five categories of results (`CodegenResult`):

| Artifact | Description | Generation Entry |
|------|------|----------|
| proto | Serialized scheduling results and other metadata | `Codegen::Generate` |
| tiling_data | Definition of the `AutofuseTilingData` structure | `Codegen::GenerateTilingData` |
| tiling | Host-side tiling function source code | `Codegen::GenerateTiling` |
| kernel | Device-side kernel function source code | `Codegen::GenerateKernel` |
| infer_shape | Host-side shape inference function source code | `Codegen::GenerateInferShape` |

The layered architecture is as follows:

```text
┌─────────────────────────────────────────────────────────────┐
│                Entry Layer (Codegen Facade)                  │
│   Generate / GenerateForInductor / GenerateTiling / ...      │
├─────────────────────────────────────────────────────────────┤
│                Kernel Generation Layer                       │
│   Kernel (graph parsing → Loop tree → loop & API call gen)   │
│   tiling_key multi-template dispatch / API source inlining   │
├─────────────────────────────────────────────────────────────┤
│                ApiCall Framework (Core Extension Point)      │
│   ApiCall base class + ApiCallFactory registration factory   │
│   ┌──────────────┐ ┌─────────────────────────────────────┐  │
│   │ Main framework│ │ v35 platform extension layer         │  │
│   │ Load/Store/  │ │ reg_api_call (RegBase)               │  │
│   │ elewise/     │ │ cube_api_call (Matmul/Conv2D)        │  │
│   │ reduce/      │ │ micro_api_call (MicroAPI)            │  │
│   │ transpose... │ │ vec_func_call (VectorFunc)           │  │
│   └──────────────┘ └─────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                Host Generation Layer                         │
│   TilingData / TilingLib (PGO, Inductor TopN, CV tiling)     │
│   InfershapeGen / GenGetKernelAndJson                        │
├─────────────────────────────────────────────────────────────┤
│                Supporting Layer                              │
│   AscendCApiRegistry (API template inlining)                 │
│   ExpressionConvertStruct (expression translation)           │
│   CheckGraphValidity (graph check) / ApiParamDump (debug)    │
└─────────────────────────────────────────────────────────────┘
```

The generation order is: Kernel first, then TilingData, Tiling, and InferShape, and finally optional PGO generation. The actual generation of the tiling part is completed by `TilingLib` through a function pointer callback to the external gen_tiling library, while Codegen is responsible for assembling and concatenating translation units.

### 6.2 Kernel Code Generation

Kernel generation is performed by the `Kernel` class (autofuse/codegen/codegen_kernel.h). One ImplGraph corresponds to one Kernel generator, which is divided into two phases: parsing and generation.

#### 6.2.1 Graph Parsing and Validity Check

Before parsing ImplGraph, `Kernel::ParseGraph` first calls `CheckGraphValidity` (autofuse/codegen/codegen_graph_check.cpp) to validate the graph, including:

- **dtype check**: Collects the input dtype combinations of nodes and checks whether the API supports them;
- **repeats/strides check**: Checks the dimensional consistency of axis, repeats, strides, and vectorized_strides;
- **node check**: Calls `IsNodeValid` of the IR codegen implementation node by node.

During parsing, Kernel registers the axes on the graph into `Tiler` (tiling data variable mapping), registers tensors/queues into `TPipe` (UB memory and queue management), and constructs the `Loop` tree (autofuse/codegen/codegen_kernel_loop.cpp) according to the node sequence, where each node in the tree corresponds to an ApiCall object.

#### 6.2.2 Loop and API Call Generation

`Loop::Generate` recursively generates the loop structure according to the splitting strategy of ImplGraph:

- **BLOCK_OUT axis** (inter-core parallel axis): Only generates size/actual_size computation without generating a for loop; parallelism is achieved implicitly via blockidx;
- **BLOCK_IN axis**: Generates `block_dim_offset` offset computation to determine the data shard processed by the current core;
- **Other axes**: Generates `for (axis = 0; axis < loop_size; axis++)` loops, and generates the actual size computation of the tail block and cache enable conditions inside the loop body.

Whenever a computation node is encountered in the loop body, the code is generated following a fixed skeleton: `WaitInputs → AllocOutputs → API call → SyncOutputs → FreeInputs → FreeUnusedOutputs`, that is, completing the wait, allocation, synchronization, and release of UB queues around the API call, ensuring the correct pipelining of MTE data transfer and Vector computation.

#### 6.2.3 Multi-Template tiling_key Dispatch

Similar to traditional operator code, for different splitting strategies, Schedule generates multiple templates corresponding to different ImplGraphs. Codegen needs to parse these templates one by one, generate template functions, and call different template functions at the kernel function entry according to tiling_key. An example is as follows:

```cpp
extern "C" __global__ __aicore__ void abs_test(GM_ADDR abs_test_Data_0, GM_ADDR abs_test_Output_0, GM_ADDR workspace, AutofuseTilingData param) {
    const AutofuseTilingData t;
    if (t.tiling_key == 0) {
        abs_test_0_general_0_nil_2_nil(abs_test_Data_0, abs_test_Output_0, workspace, t);
    } else if (t.tiling_key == 1) {
        abs_test_0_general_0_nil_2_nil_unaligned(abs_test_Data_0, abs_test_Output_0, workspace, t);
    }
}
```

An example of the above `AutofuseTilingData` structure is as follows. The concrete values of its member variables, including tiling_key, are computed and provided by ATT:

```cpp
BEGIN_TILING_DATA_DEF_T(AutofuseTilingData)
  const uint32_t block_dim = 40;
  const uint32_t corenum = 0;
  const uint32_t ub_size = 196352;
  const uint32_t hbm_size = 0;
  const uint32_t tiling_key = 0;
  const uint32_t z0z1z2z3t_size = 17968;
  const uint32_t z0z1z2z3Tb_size = 57;
  const uint32_t q0_size = 96;
  const uint32_t q1_size = 35936;
  const uint32_t q2_size = 35936;
  const uint32_t b0_size = 35936;
  const uint32_t tmp_tbuf_size = 8192;
END_TILING_DATA_DEF_T;
```

Different template functions generate different for loops and different amounts of data processed each time. Examples are as follows:

- **tiling_key=0**

Splitting along the z1 axis; the vectorized axis completing computation in UB each time is z1t.

```text
for (int z0z1Tb = 0; z0z1Tb < z0z1Tb_loop_size; z0z1Tb++) {
    Abs(y_local[0], xlocal[0], z1t_actual_size);
}
```

- **tiling_key=1**

Splitting along the z0 axis; the vectorized axes completing computation in UB each time are z0t and z1.

```text
for (int z0Tb = 0; z0Tb < z0Tb_loop_size; z0Tb++) {
    Abs(y_local[0], xlocal[0], z0t_actual_size * z1_axis_size);
}
```

`Kernel::GenKernelFuncByTilingKey` selects different dispatch implementations according to the scenario:

- **Register-based tiling_key** (static shape): The tiling_key is written into a register; each scheduling template generates a kernel function, and a dispatch chain `if (t.tiling_key == N) { ... }` is generated at the entry. When multiple templates in a group need to run in parallel, `SyncAll()` synchronization is inserted;
- **Parsing tiling_data** (dynamic shape / Inductor): The tiling_data structure is parsed at runtime to select a branch;
- **CV fusion**: Generates multi-group CV kernel functions;
- **Template overflow**: When the number of tiling_keys exceeds the limit of a single compilation unit, they are automatically split into multiple compilation units (PackingFunc) for separate compilation.

#### 6.2.4 API Source Inlining

The implementation source code of the AscendC APIs called in kernel files (such as `DataCopyPadExtend`, `Abs`, etc.) is managed uniformly by `AscendCApiRegistry` (autofuse/codegen/ascendc_api_registry.cpp). At build time, each API header file is packed into a source string and registered into a singleton table. When generating a kernel, the API source strings are directly inlined into the kernel file according to the header file dependencies declared by nodes, making each kernel source file self-contained and independently compilable.

### 6.3 Host Code Generation

#### 6.3.1 tiling_data Generation

`TilingData::Generate` (autofuse/codegen/codegen_tiling_data.cpp) generates the definition of the `AutofuseTilingData` structure, whose fields include tiling_key, block_dim, workspace size, sizes of each split axis, etc.; in multi-ScheduleGroup scenarios, a unified wrapper structure is generated. For the static shape Inductor scenario, a full-const initial value version is also generated, moving tiling computation forward to compile time.

Workspace sizes and byte offsets use `uint64_t`, so a single workspace larger than 2 GiB and an accumulated size larger than 4 GiB are not truncated. The direct tiling ABI uses `uint64_t *workspace_size`; host-side accumulation and 512-byte alignment use checked calculations and return failure on overflow. Non-Inductor direct tiling retains the existing 16 MiB reserved-workspace semantics after workspace accumulation.

#### 6.3.2 tiling_func Generation

The Host-side tiling functions are organized and generated by `TilingLib` (autofuse/codegen/codegen_tiling.cpp), including `AutofuseGetTilingSize` (estimates the memory required by tiling), `AutofuseTiling` (the main tiling function that computes tiling_key and the split sizes of each axis according to shapes), workspace computation, and other functions. In addition to regular generation, the tiling side also supports:

- **PGO generation**: Generates a standalone tiling search executable that traverses tiling candidates on real hardware, collects performance, and saves the best result;
- **Inductor TopN selection**: Combines performance modeling formulas (provided by ATT, latency ≈ API call count × per-call latency) with measured profiling to perform modeled evaluation and TopN screening of tiling candidates;
- **CV fusion tiling**: Generates dedicated tiling functions and auxiliary interfaces for Cube/Vector fusion scenarios.

#### 6.3.3 infer_shape Generation

`InfershapeGen::GenInferShapeFunc` (autofuse/codegen/codegen_infershape.cpp) generates the `extern "C" InferShape` function: it parses the symbolic variables in each output shape expression and generates the inference code of per-dimension AppendDim; for expressions containing division rounding, it additionally generates rounding and precision validation logic, ensuring that shape inference under dynamic shapes is consistent with the actual computation of the kernel.

#### 6.3.4 get_kernel Generation

`Codegen::GenGetKernelAndJson` reads the compiled kernel binary (ota) and generates the `extern "C" void GetKernelBin(std::vector<char>&)` function, embedding the Device code into the Host-side source in binary form for direct loading at runtime, avoiding runtime compilation overhead.

### 6.4 ApiCall Framework

Each node on ImplGraph is eventually converted into an API call. This conversion is carried by the ApiCall framework, which is the core extension point of Codegen.

#### 6.4.1 Base Class and Generation Chain

All ApiCalls inherit from the base class `ApiCall` (autofuse/codegen/codegen_kernel_loop.h). The core generation chain is:

```text
Init(node)                 // Collect unit, input/output tensors, tmp_buf information
  → ParseAttr()            // Overridden by subclasses to parse operator attributes
  → BuildApiParam()        // Assemble CodegenApiParam (loop axes, offset, cal_count, etc.)
  → GenerateApiCallString()// Concatenate the API call string according to api_param
  → PostProcess()          // Generate final synchronization code
```

`CodegenApiParam` is the intermediate representation of API input parameters. It translates the symbolic expressions (`ge::Expression`) on the graph into C++ expression combinations of tiling variables and loop variables via `ExpressionConvertStruct` (autofuse/codegen/expression_convert_struct.cpp), such as `cal_count`, offsets, and loop sizes.

The base class also provides UB lifecycle helper interfaces (`WaitInputs/AllocOutputs/SyncOutputs/FreeInputs`, etc.), handling shared queue reuse and MTE2/MTE3 synchronization. Subclasses usually only need to override `BuildApiParam` and `Generate` to integrate a new operator.

#### 6.4.2 Factory and Registration Mechanism

The creation of ApiCall adopts the static self-registration factory pattern (autofuse/codegen/api_call/utils/api_call_factory.h):

- Each ApiCall implementation class defines a static `ApiCallRegister<T>` object at the end of the file, registering "class name → constructor" into the singleton factory `ApiCallFactory`;
- On the IR definition side (ascir codegen impl), the node's corresponding ApiCall class name is declared via `GetApiCallName()`;
- When kernel generation traverses nodes, ApiCall objects are created from the factory by class name. The main generation flow is unaware of specific operator implementations; adding a new operator only requires adding an implementation class and registering it.

#### 6.4.3 Built-in ApiCalls

The built-in ApiCalls of the main framework (autofuse/codegen/api_call/) are organized by computation category:

| Category | ApiCall |
|------|---------|
| Data transfer | `LoadApiCall`, `StoreApiCall` |
| Unary computation | `UnaryApiCall`, `CastApiCall`, `RsqrtApiCall`, `LogicalNotApiCall`, `UnaryBitWidthChangeApiCall`, etc. |
| Binary computation | `BinaryApiCall`, `AxpyApiCall`, `TrueDivApiCall`, `PowApiCall`, `LeakyReluApiCall`, etc. |
| Comparison and selection | `CompareApiCall`, `WhereApiCall`, `ClipByValueApiCall` |
| Reduction | `ReduceApiCall` |
| Data rearrangement | `TransposeApiCall`, `BroadcastApiCall`, `ConcatApiCall`, `GatherApiCall` |
| Others | `PadApiCall`, `RemovePadApiCall`, `Ub2UbApiCall`, etc. |

### 6.5 v35 Platform Extension Layer

Different SoC versions differ in hardware instruction sets and API forms. Codegen carries version-specific implementations through the platform extension layer (autofuse/v35/codegen/). The extension layer fully reuses the base classes and registration mechanisms of the main framework: each implementation class also inherits `ApiCall` and is statically registered into `ApiCallFactory`; SoC version routing selects implementations at the IR registry level according to chip version, while the kernel generation flow itself remains platform-independent.

The v35 extension layer contains four categories of implementations:

#### 6.5.1 reg_api_call: RegBase-Style APIs

RegBase-style APIs are vector computation and data transfer APIs in the RegTensor instruction form, and are the main body of v35, including about 24 classes such as `BinaryApiCallV2`, `CastV2ApiCall`, `CompareV2ApiCall`, `LoadRegApiCall`, `StoreRegApiCall`, `NddmaApiCall`, `IndirectLoadRegApiCall`, `BroadcastRegApiCall`, `ConcatRegApiCall`, `SplitRegApiCall`, `RegReduceApiCall`, `TransposeRegApiCall`, `GatherRegApiCall`, `WhereRegApiCall`, and `SoftmaxApiCall`. Compared with the main framework versions, the V2 series APIs have stronger parameterization capabilities (such as axis merging merge_axes), and compute `outer_call_count` (the number of outer API calls) in `BuildApiParam`. This value directly connects to the performance formula modeling of Auto Tiling (latency ≈ call count × per-call latency) as input for tiling candidate evaluation.

The corresponding API source templates (about 100 RegBase APIs) are automatically packed into strings from source headers at build time and registered into `AscendCApiRegistry` (autofuse/v35/codegen/ascendc_reg_base_api_register.cpp).

#### 6.5.2 cube_api_call: Cube Operator APIs

`MatmulApiCall` and `Conv2DApiCall` generate AscendC API calls for Cube operators such as Matmul/Conv. In addition to generating call sites, Cube unit calls also generate template function definitions (`GenerateFuncDefinition`) and macro expansion (`GenerateMacro`), and connect to the official matmul tiling implementation through a tiling wrapper. The related Cube API templates (matmul, batch_matmul, conv2d and their dynamic/tiling_key/pingpong variants) are registered in autofuse/v35/codegen/ascendc_cube_api_register.cpp.

#### 6.5.3 micro_api_call: MicroAPI

MicroAPI is the lowest-level code form, directly generating `AscendC::MicroAPI::*` instruction-level calls (such as `LoadAlign`, `StoreAlign`) and `AscendC::Reg::*` register operations (such as `Pack`, `UnPack`, `MaskPack`). It is carried by the independent `MicroApiCall` base class and `MicroApiCallFactory` (not inheriting the main framework `ApiCall`), including `MicroLoadApiCall`, `MicroStoreApiCall`, `MicroCastApiCall`, `MicroCompareApiCall`, `MicroWhereApiCall`, `MicroBinaryScalarApiCall`, `MicroScalarBroadcastApiCall`, etc.

#### 6.5.4 vec_func_call: VectorFunc

`VfCall` wraps a subgraph in ImplGraph into an independent vf function, achieving the structural optimization of "multiple loops → one function call". It internally holds the `VFLoop` loop tree; when traversing subgraph nodes, it creates a MicroApiCall for each node through the MicroAPI factory, forming a two-layer structure:

```text
VfCall (main framework ApiCall, generating function definitions and call sites)
  └── VFLoop (loop tree inside vf)
        └── MicroApiCall (instruction-level API calls)
```

This mechanism also supports kernel generation for the CV-UB fusion scenario.

### 6.6 Supporting Mechanisms

- **API parameter dump**: `CodegenApiParam::DumpGraphApiParams` (autofuse/codegen/codegen_api_param_dump.cpp) can serialize the API input parameters of all nodes in each ImplGraph into text files, used for debugging and comparing generated call parameters. When developing a new ApiCall, this tool can be used to verify whether parameter assembly is correct.
- **Expression conversion**: `ExpressionItem/CombinedExpression` provide unified rendering from symbolic expressions to C++ code, with factory functions (`ExprItemFactory/CombinedExprFactory`) for assembling common expression patterns (such as the `SizeMinusActualSize` tail block computation).

### 6.7 Semantic Naming Requirements for New Templates

New templates, implementation strategies, API selection or fallback branches, and naming-related changes to grouping, graph rewrites, or reuse mappings must adapt `semantic_name`. If only tile size, core count, dtype, or buffer count changes without changing the implementation category, explain why the existing name still applies; do not create categories for numeric combinations.

The format below uses brackets for optional parts, `|` between API features, and `+` between successful transformations:

```text
<family>/<strategy>[@<role>][#<api-feature>|...][+<transform>+...]
Reduce/RCore@Phase1
Reduce/Common@Norm#AR|NoReuseSrc
Concat/UB#OneAxis
IndirectLoad/SIMT@Strided#Offset32
```

`family` identifies the implementation family, `strategy` the implementation strategy, `role` the logical phase or responsibility, `api-feature` the final API implementation feature, and `transform` a successful graph or data-movement transformation. Numeric parameters remain in the original tiling information. The protocol uses `semantic_schema=1`; fields and names have no `v2` suffix.

- **Single source**: Define vocabulary in `ascgen_utils::template_semantic` in `autofuse/common/common_utils.h`; use shared helpers for enum-to-name mappings too. Selection sites reference shared constants and retain their original selection conditions. `NormalizeTemplateSemanticName()` in `common_utils.cpp` normalizes names once when generating `ModelInfo`. ATT, TopN, summary, and offline tools consume normalized values without maintaining separate role tables, reclassifying implementations, or duplicating template selection. Do not infer implementations from Torch operator names, test labels, graph names, or generated source.
- **Collection and propagation**: Schedule records strategies, group roles, and successful transformations under the [semantic propagation rules](schedule.md#template-semantic-propagation). Codegen records features through `CodegenApiParam.semantic_feature` or the existing `SetSemanticFeature` at the successful final API selection point. Clear or replace stale information after fallback; do not retain failed-branch tags.
- **Identity and lifetime**: Associate names with the current invocation, candidate, and complete graph/result/group/key/subcase/template identity. Restore the current logical identity after reuse. Commit final selection snapshots together with the winning tiling data; neither `group_id` alone nor the last selection of a shared primary establishes ownership. For cache/PGO paths without an exact snapshot, fall back using the current key without borrowing historical state or solving again.
- **Uncertainty**: Use a parent name or `Adaptive` only for stated conditions such as an unresolved runtime branch or missing final API information in standalone `GenerateTiling`, with corresponding tests. Report non-unique identity matches as `ambiguous` and missing information as `unavailable`; default parent names or `Adaptive` must not hide missing integration.
- **Behavior and performance**: Observation must not change public ABI, tiling/cache data, candidate selection, or real solver exceptions; diagnostic failures only disable or degrade observation. With INFO disabled, avoid added diagnostic string and snapshot-container construction. Do not add solving, graph scans, IO, or kernel launches. Retain existing functional, compilation, tiling, and kernel performance gates without relaxing thresholds. Measure performance with INFO disabled and report observation overhead separately with INFO enabled; explicitly list checks not run.

The design and PR description for a new template or branch must state its category or inheritance rationale, actual collection points and copy/invalidation/fallback timing, complete identity and reuse handling, uncertainty states, test entry points, actual branches, expected names, and code/artifact versions. Explain items that do not apply.

Reuse existing UT and backend/generated-code execution tests to verify the correspondence between actual APIs or branches, complete identity, names, and states; non-empty strings or file existence alone are insufficient. Cover boundaries affected by the change: copying, failure, fallback, multiple groups/reuse (including equal group IDs across graphs/results), multiple subcases for one key, cache/PGO, INFO disabled, and diagnostic failures. Record naming integration, device execution, accuracy, and performance separately; TopN candidate coverage does not establish device execution or accuracy.

These are development and review requirements. Automatic CI checks linking template registrations to naming tests remain to be implemented. Do not maintain a duplicate full template inventory or claim that current CI automatically rejects every omission.
