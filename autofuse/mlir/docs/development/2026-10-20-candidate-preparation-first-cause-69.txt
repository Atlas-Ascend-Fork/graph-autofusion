# 候选准备那道闸门的首因 —— 69 格逐格量出（2026-10-20）
#
# 这 69 格是 legacy 接管表上 `state=hard-failure` 且 `gate=candidate-preparation` 的全部格子
# （reg 侧 55 + mem 侧 14，取自 2026-10-19-legacy-takeover-table-reg-m1.txt 与
# 2026-10-17-legacy-takeover-table-mem.txt）。它们占全部硬失败 87 格的八成，而在这次量之前
# **「第一条诊断」一栏全是空的**：那道闸门的理由只走 `GELOGW`，而 legacy e2e 把 dlog 调到
# ERROR，看不见。
#
# 这次只做两件事，都不改行为：
#   1. `PlanSelection.cpp` 三条 `TemplateSupportsMlir*` 谓词各自答得出「为什么不行」；
#   2. `ReportStrictVerdict` 在严格模式下把下降之前那几道闸门自己的诊断按 `error: <理由>`
#      打到 stderr。
#
# **没碰行为的判据已验**：69 格的 `state` / `gate` / `shortfall` 三列与基线逐格比，`diff` 为空。
#
# 量具（build 要在 legacy ST 那一档；本机那一档必须 -j 2，-j 6 会 OOM。aihac_codegen 是动态库，
# 库编完之后这 69 格可以 --no-build 跑，不必重链）：
#   bash autofuse/mlir/test/probe/legacy_takeover_table.sh --no-build -R '<69 格的正则>'
#
#===----------------------------------------------------------------------===#
# 首因分桶
#
#   桶                          格数   mem   reg
#   --------------------------------------------
#   queue-resources              28     2    26
#   att-tiling-key               27    11    16
#   elementwise-broadcast        11     0    11

#   --------------------------------------------
#   合计                         69    14    55
#
# **设计文档对这 69 格的归因（「concat / topn / reduce / int64 比较这些节点类型 MLIR 本来就
# 没建模」）不成立。** 两条理由：
#
#   1. 候选枚举那三条谓词**一条都不看节点类型**，它们是形状 / 布局 / 队列判据。所谓「节点类型
#      没建模」在这道闸门上没有对应的判据。
#   2. 27 格（四成）**根本不在候选枚举上**。它们过了 plan selection，死在 `RunAttForCandidates`
#      之后的 tiling 字段校验（`AttSchemaAdapter.cpp:130`）。文档点名的 `concat_test` /
#      `brc_reduce_test` / `gather_reduce_store_test` 恰好都在这一桶。
#
# 四个桶的性质各不相同，所以 **F-4 不能按文档那一条修法做**（把枚举失败统一标成能力不足）：
# 那样会把 att-tiling-key 那 27 格的缺陷一并埋进「能力不足」里。
#
#   - att-tiling-key（27 格）：**看起来是缺陷，不是能力不足。** 诊断是 ATT 生成的 tiling_func
#     引用了 `graph0_tiling_key` 与 `tiling_key`，而 `TilingFieldSchema` 里没有这两个名字。
#     `tiling_field_schema.cpp:147` 发的是 `tiling_key`（flat）或 `graph<N>_result<M>_tiling_key`
#     （嵌套）两种拼法之一，ATT 那边引用的是第三种 `graph0_tiling_key`——**两侧拼法对不上**。
#     这道校验本身是防静默错编的（注释写在 `AttSchemaAdapter.cpp:107`），不该放开。
#     **哪一侧的拼法是对的还没判**，要读 ATT 的 tiling_func 生成器，那是独立一步。
#   - queue-resources（28 格）：同一个 queue id + reuse id 上挂了两份不同的 tile view。调度
#     确实给了两份，MLIR 的资源 verifier 收不了——这一桶有可能是真的能力不足，但**要逐格确认
#     是「调度给的」还是「我们读错了」**。
#   - elementwise-broadcast（11 格）：某个 elewise 节点的某个输入广播不到输出视图。全在 reg 侧。
#   - data-movement（3 格）：局部 tile 收不成一段。**这一桶比预期小得多**——开量之前怀疑
#     `TemplateSupportsMlirDataMovement` 在 `afir.nddma` 接通之后变成过度拒收，69 格里它只命中
#     3 格，那条怀疑按量级不成立。
#
