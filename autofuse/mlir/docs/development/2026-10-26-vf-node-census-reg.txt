# VectorFunc 普查 —— reg 侧（NpuArch 3510 / Ascend950PR_9599），2026-10-26 重量
#
# 上一张是 2026-10-17-vf-node-census-reg.txt。重量的理由：本期补过 12 个 bf16 用例样板漏设的
# `Output` dtype（`tests/framework/share_graph/src/share_graph.cc`），那是**输入图**的改动，
# 调度融不融 VF 可能跟着变，所以 110 这个数不能照抄。
#
# 量具: autofuse/mlir/test/probe/vf_node_census.sh -t <2026-10-26 的 reg 全量接管表>
# 代码: 6a525700 + 本期两个广播补丁（bf16 开位、形态 B 带填充），在隔离 worktree
#       /mnt/workspace/agent/claude/brc-bf16-wt 上量。环境: 远端 AF_MLIR_0814。
#
# 汇总: 含 VF 110 / 不含 VF 90，没产出 0 —— **与 10-17 那张逐个相等**。所以那 12 行 Output
# dtype 没有改变调度的 VF 融合，设计文档「110 不应该因本设计而变」这条回归口径成立。
#
# **变的是它的内部分布，而那才是排期该看的数**（左列含不含 VF，上行是接管表状态）：
#
#                 takeover   fallback(首因是 VF)   fallback(其他)   hard-failure   out-of-scope
#   含 VF  110        24              8                  27              50             1
#   无 VF   90        39              —                  34              16             1
#
#   10-17 那张的含 VF 一行是：takeover 0 / 首因是 VF 17 / 其他 34 / hard-failure 58 / oos 1。
#
# 三条结论：
#
#   1. **「只差 VF」17 -> 8 格。** 接 VF 的直接收益降了一半多。
#   2. **「VF 是那 55% 的必要条件」已被实测否证。** 旧文档原话是「不接它，补 op、补 dtype
#      一格也换不回来」；实际本期补 op / 补 dtype 换回来的 48 格里有 **24 格是含 VF 的**。
#      成因：普查是**关掉 MLIR** 量的（口径见脚本头部第 1 条），量的是「legacy 调度融不融
#      VF」；MLIR 开着时 plan selection 可能选到另一个不含 VF 的 plan。所以「legacy 侧含
#      VF」不等于「MLIR 这条路非接 VF 不可」。
#   3. 含 VF 但被更早缺口挡住：93 -> 78 格（27 fallback + 50 hard-failure + 1 oos）。其中
#      **50 格是硬失败**，首因在 plan selection 那一层（与功能需求 6 的 F-4 同族），量级比
#      VF 自己大得多。
#
# 今天那 8 格「只差 VF」的成因只有两类：
#   - 6 格卡 VF 的 dtype 白名单（bf16 四格 abs/abs_fma/add_exp/truediv，uint8 两格 abs/relu）；
#   - 2 格卡 VF 子图里的 `Scalar` 节点没建模（abs_brc_add、load_compare_scalar_where_store）。
#
# **量具这一轮修过一处**：`first_is_vf` 原先只认 `of type 'VectorFunc'` 这一种措辞，而本期
# VF 那道闸门的诊断换成了按 dtype / 按子图节点分的两条，于是「只差 VF」静默读成 0 格。改法
# 与理由记在脚本里那条判据上面。**先读到 0 的那一版不是结论，是假 0。**
#
