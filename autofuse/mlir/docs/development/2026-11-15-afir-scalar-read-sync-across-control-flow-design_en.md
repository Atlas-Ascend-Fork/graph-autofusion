# Introduction

## Purpose

Fix synchronization-source lookup for scalar reads in MLIR codegen. The previous lookup could miss writers in another conditional block or loop body and fail implementation selection. This design analyzes writer pipelines before AFIR compute operations are lowered and records the result as an attribute shared by capability queries and lowering.

Audience: developers and reviewers of Autofuse MLIR AFIR, AFIRToAscendC, and synchronization.

Expected output: storage matching rules, writer-analysis scope, synchronization attributes, multiple-event emission, and validation boundaries.

## Scope

Includes storage analysis and scalar-read synchronization in `Synchronization.{h,cpp}`, the new `AFIRScalarReadSync` pass, and the callers in `Broadcast.cpp`, `BinaryElementwise.cpp`, and `TernaryElementwise.cpp`.

Does not change guard granularity in `AFIRExecConditionPass`, move producers, or change legacy synchronization rules. Existing modules continue to own cross-core synchronization, queue depth, and double-buffer event pairing. Broadcast source pitch and inner padding in the same PR are layout support and are outside this synchronization design.

The affected components are Autofuse AFIR and AFIRToAscendC. SuperKernel is unaffected.

# Overview

## Software Overview

### Project Context

In historical fuzz reruns on 2026-11-14, 22 of 45 failing seeds first reported an error at `afir.broadcast`; six involved scalar reads across conditional blocks. A representative structure, with descriptors omitted, is:

```mlir
%storage = ascendc.que_bind.alloc_tensor %queue
%scalar_buffer = ascendc.local_tensor.reinterpret_cast %storage
scf.if %guard {
  afir.truediv %input, %divisor outs(%scalar_buffer)
}
afir.pipe_barrier vector
scf.if %guard {
  afir.broadcast %scalar_buffer outs(%output)
}
```

`AFIRExecConditionPass` creates a separate `scf.if` for each operation. The previous `findWriterEvent` only scanned preceding operations in the current block and could not find a writer inside the preceding conditional. In addition, writer-side `alloc_tensor` and reader-side `deque_tensor` return different SSA values, so comparing tensor values does not identify shared storage.

Lowering introduces another problem: already lowered writers no longer carry AFIR traits. Reanalysis may omit their pipelines. Capability queries and lowering can therefore produce different answers even when calling the same helper.

An existing `afir.pipe_barrier vector` only orders the V pipeline. It cannot replace V-to-S synchronization because `GetValue(0)` executes on S. Binary and ternary elementwise scalar inputs use the same helper and are affected as well.

### Product Environment

The design affects AscendC source generated by `libaihac_codegen.so`. Scalar reads still emit `FetchEventID`, `SetFlag`, and `WaitFlag`, followed by `GetValue(0)`. No runtime or aclrt interfaces, Python packages, run packages, or installation paths change.

## Functionality

1. Identify writers by storage container, including writers in sibling `scf.if` operations, loop bodies, or later in program order.
2. Record a deduplicated pipeline set when multiple pipelines write the same storage, and synchronize each pipeline.
3. Preserve analysis results before compute lowering so that lowering order cannot change event selection.
4. Continue rejecting unknown synchronization sources; use a restricted container fallback only when no writer is found in the function.

## Constraints

- **Drain semantics:** consecutive `SetFlag` and `WaitFlag` operations wait for work issued on the specified pipeline before the synchronization point. Analysis collects possible writer pipelines without proving equal control-flow conditions. Synchronization does not initialize input data or make future writes complete early.
- **Conservative synchronization:** missing a required event can produce incorrect values; additional events may increase waiting time.
- **Event slots:** `FetchEventID` does not reserve a slot. Each `SetFlag` is immediately followed by `WaitFlag`, without overlapping waits for events of the same type.
- **Determinism:** sort the pipeline set by `afir::Pipe` enum value, independently of hash iteration or pointer addresses.
- **Pass order:** analyze after resource materialization and before implementation selection. Lowering only reads recorded attributes.
- No default high-volume logging or public ABI/API changes.

## Assumptions and Dependencies

- `AFIRDestinationStyleInterface` and `getOperandPartition` enumerate destinations of AFIR writers within a function.
- Retain the existing pipeline classification: `AFIRTransferIn` maps to MTE2, `AFIRTransferOut` to MTE3, and other supported writers to V.
- Queues and TBufs represent storage. Enqueue/dequeue operations may break tensor-level SSA associations.
- The container fallback preserves compatibility with external writes or manually constructed IR fragments. It does not analyze writes across functions and depends on existing position conventions.

# Requirements and Design

## Overall Design

```text
LoopGenerate → MemoryAllocate → PipelineSync → ScalarReadSync → ExecCondition → Selection → Conversion
                                             record attributes                          read attributes
```

“Before lowering” means AFIR compute operations still retain their traits. Resource materialization has already introduced AscendC queue and TBuf operations; the IR is not entirely free of target-dialect operations.

## Functional Requirements

### Requirement 1: Collect Writer Pipelines by Storage

1. Description

   Given an operation and an input index, collect pipelines that write the input's storage without filtering by control-flow position.

2. Inputs

   `Operation *anchor` and `unsigned inputIndex`. The input must belong to the operation's input partition and have `ascendc::LocalTensorType`.

3. Processing

   Trace reinterpret casts, single-destination AFIR operations, and queue/TBuf tensor-access operations to the storage container. Walk the enclosing `func.func`, compare destination storage roots, classify matching writers by trait, deduplicate, and sort.

   Multiple members of one queue may share the same storage identity, conservatively including pipelines that write other members. The analysis does not provide precise member-level alias information.

   A matching `AFIRTransferOut` writer causes failure, preserving existing unsupported behavior. If no writer is found, allow fallback only for tensors obtained through `deque_tensor` or `tbuf.get_tensor`: VECIN maps to `TransferIn`, and TBuf to `Vector`. An unwritten `alloc_tensor` has no fallback.

4. Outputs

   `FailureOr<SmallVector<afir::Pipe>>`. Failure means the input or writer type is unsupported; a successful empty set means the synchronization source is unknown.

### Requirement 2: Carry Results from Analysis to Lowering

1. Description

   Record results before implementation selection. Do not rescan mixed IR during lowering.

2. Inputs

   AFIR operations outside `afir.vector_func`. A potential scalar-read input must be a local tensor whose repeat is provably 1 on every vectorized axis.

3. Processing

   Store `afir.scalar_read_sync` as an array indexed by input position. Each entry contains that input's `#afir<pipe ...>` list, for example `[[], [#afir<pipe vector>]]`. Omit the attribute when every entry is empty.

   Capability queries prefer the attribute. Standalone `--afir-select-implementation` queries may analyze unlowered compute operations when the attribute is absent. Lowering only reads the attribute; missing or invalid data means no usable synchronization source.

4. Outputs

   Operation attributes and corresponding event sets, inspectable through IR dumps and lit checks.

### Requirement 3: Emit Multiple Synchronization Events

1. Description

   Wait for every relevant pipeline before reading a scalar.

2. Inputs

   Source tensor, event set, and insertion point.

3. Processing

   Reuse the function's existing `TPipe`. For each event, emit `FetchEventID`, `SetFlag`, and `WaitFlag`, then emit one `GetValue(0)`. An empty event set or missing `TPipe` causes failure.

4. Outputs

   N synchronization sequences followed by one scalar read. N = 1 retains the existing call form.

## Nonfunctional Requirements

### Maintainability

Keep storage analysis and event emission in `Synchronization.cpp`, shared by all three callers. Pipeline-to-`HardEvent` conversion reuses `kHardEventTable` rather than introducing another mapping.

### Testability

lit checks analysis, selection, and lowering across conditional blocks, plus multiple-pipeline membership and ordering. Existing singleton positive and negative cases provide regression coverage. This change adds no standalone analysis UT. CPU simulation can validate values, but sequential execution cannot prove real cross-pipeline synchronization; NPU validation is required for that property.

### Portability

No new chip-model conditions. Event availability continues to use `kHardEventTable`.

### Reliability

Check attribute lengths and types before access. Unknown sources and unmappable events reject the implementation as a whole rather than emitting an incomplete synchronization sequence.

## Performance

### Compilation Time

Each input satisfying the annotation conditions triggers a function walk. With N operations and S candidate inputs, total work is approximately O(S × N), plus storage-root tracing and expression proofs. Results are not cached. No dedicated compilation-time measurement is available, so negligible overhead is not an established conclusion.

### Execution Performance

Single-event cases retain the existing synchronization form. Multiple writer pipelines add events, and container-level matching may broaden the wait scope. No data movement is added. Actual synchronization overhead requires NPU measurement.

### Memory and Artifact Size

The pass adds temporary pipeline sets and operation attributes whose size grows with the number of candidate inputs. No separate memory or artifact-size measurement is available.

## Interface Design

### Added and Modified Interfaces

All interfaces are internal and declared in `Implementations/Synchronization.h`:

- `analyzeScalarWriterPipes(Operation *, unsigned)` returns `FailureOr<SmallVector<afir::Pipe>>` and analyzes storage writer pipelines.
- `scalarReadEvents(Operation *, unsigned)` returns `SmallVector<ascendc::HardEvent>` for capability queries, permitting analysis when the attribute is absent.
- `recordedScalarReadEvents(Operation *, unsigned)` returns the same event type for lowering and only reads attributes.
- `materializeScalarRead(Operation *, Value, ArrayRef<ascendc::HardEvent>, RewriterBase &)` returns `FailureOr<Value>` and emits synchronization and the scalar read.
- `createAFIRScalarReadSyncPass()` and `registerAFIRScalarReadSyncPass()` create and register the pass.

## Software Design

### Key Data Structures

`StorageRoot` contains the storage-container value and a `handedOver` flag used only for restricted fallback. Analysis returns an `afir::Pipe` set, which is converted to `HardEvent` values for emission. `afir.scalar_read_sync` is an input-indexed `ArrayAttr` retained on the operation between analysis and lowering.

### Key Algorithms and Decisions

Analyze early and preserve the result as an attribute. Expanding only the lowering-time lookup would require a separate pipeline classification for target-dialect operations, while still allowing different results between stages. The selected design reuses AFIR traits when the information is complete.

The pass belongs in `conversion/AFIRToAscendC/` because storage tracing depends on AscendC queues, TBufs, and reinterpret casts. That dependency must not be introduced into AFIR transforms. Add the attribute name to the known-attribute list in `AFIR.h` to pass unknown-attribute validation.

### Processing Flow

Walk functions and record writer pipelines for potential scalar-read inputs. Implementation selection queries event availability. Lowering reads the recorded result, synchronizes each pipeline, and reads the scalar.

No writer without valid fallback, TransferOut writers, unavailable attributes, and unmappable events follow existing capability or lowering failure paths. Whether the caller falls back to legacy depends on `mlir_codegen_config`; this pass does not guarantee fallback. The pass does not move operations and needs no structural rollback.

### Error Handling

#### System Errors

No direct device-memory allocation, file access, or new runtime calls. Existing containers manage temporary collections.

#### Interface Errors

Invalid partitions, types, or attributes return failure or an empty set. Capability queries report `CapabilityReason::MissingInformation`; lowering uses `notifyMatchFailure` for unsynchronizable scalar reads. Additional storage-root diagnostics are not guaranteed.

# Safety Review

Checked against `docs/guidelines/编码红线.md`: no new sensitive data, platform conditions, or high-frequency logs; indexed attribute access checks bounds and types; no new size arithmetic or device allocations; events are immediately paired without cross-region ownership; public ABI/API and ASCIR dependency edges remain unchanged; set order is deterministic.

Container position is only a restricted fallback. When a writer exists in the function, use its actual pipeline to avoid mapping Vector-written VECIN storage incorrectly to `MTE2_S`.

# Compatibility Review

Script arguments, configuration format, installation layout, and public interfaces remain unchanged. Existing single-event paths retain their call form; multiple-pipeline synchronization may add waits. Unknown sources remain unsupported, with errors and fallback determined by the existing call chain.

# Test Design

## Boundaries

lit entry points are `--afir-scalar-read-sync`, `--afir-select-implementation`, and `--afir-to-ascendc-pipeline`, using handwritten AFIR without runtime mocks. CPU E2E checks generated code and values; NPU tests check real asynchronous pipeline synchronization. `load_broadcast_scalar_read_sync.py` is registered in the NPU manifest and reuses the common runner. No standalone analysis UT was added.

## Commands

After configuring the build according to the MLIR README and loading the CANN environment:

```bash
cmake --build build --target check-lit-mlir -j 8
bash scripts/test/run_autofuse_test.sh -u -s -m mlir -j 8
```

The first command covers lit. The second covers MLIR UT, lit, ST, and CPU E2E, without real NPU execution.

On an NPU with matching sources, build artifacts, and CANN configured:

```bash
python3 autofuse/mlir/test/e2e/npu/run.py --id load_broadcast_scalar_read_sync --mode both
```

The case disables profiling by default and compares every element exactly. `both` runs legacy before MLIR. Generated-code checks apply only to the MLIR route and reject stale caches or unfused execution. Offline tests reject the wrong pipeline, missing waits, a shared conditional block, and an incorrect scalar.

On 2026-11-16, this case passed on an NPU with CANN 9.3.0: NPU eager, legacy, and MLIR matched every CPU reference element exactly. The MLIR generated-path check passed with `gate=none shortfall=no` and one newly generated fused kernel. This result covers only the fixed shapes of this regression case.

# Acceptance Criteria

1. Cross-conditional cases record correct pipelines, select scalar implementations, and emit matching synchronization.
2. Multiple-pipeline cases record a complete, ordered set; existing unknown-source negative cases remain rejected.
3. Relevant lit and CPU E2E pass. Full-suite results identify commands and revisions, separating historical evidence from current validation.
4. Cross-conditional scalar reads pass value comparison on a real NPU; CPU success does not replace this requirement.
5. Documentation matches interfaces, fallback rules, and actual test scope, and retains unverified items for the current run.
