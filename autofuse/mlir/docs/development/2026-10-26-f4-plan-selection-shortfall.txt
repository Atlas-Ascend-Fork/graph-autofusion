# F-4：候选准备那道闸门答得出「不支持」—— 首因归属与标记后的全量表（2026-10-26）
#
# 两半，分两步做，第二步的范围由第一步的清单定：
#
#   第一步（归因）：让那 55 格报出首因。
#   第二步（标记）：只把其中「模板判据」那一类标成能力不足，于是它们从硬失败变成干净回落。
#
#===----------------------------------------------------------------------===#
# 为什么 55 格原先无诊断
#
# 不是没算出理由。`PrepareMlirCandidates` 四个失败出口每一个都填了 `diagnostic`，但它只走
# `GELOGW`，而 legacy 的 e2e 用例把 dlog 调到 ERROR，W 级一句都看不到。下降那一侧的理由是
# stderr 上的 MLIR 诊断，所以表里只有它那一列有首因。
#
# 改法：严格模式下把闸门自己的诊断按 `error: <理由>` 打到 stderr（`ReportStrictDiagnostic`）。
# 前缀对齐量具里 `grep -m1 -o 'error:.*'`，**接管表的量具一行都没改**。缺省档不多输出一个字节。
#
#===----------------------------------------------------------------------===#
# 首因分桶（reg 侧 55 格）
#
#   桶                      格数   性质
#   --------------------------------------------------------------------
#   queue-resources          26    能力不足：同一 que id + reuse id 上两份不同的 tile view
#   att-tiling-key           16    **缺陷，不是能力不足**（见下）
#   elementwise-broadcast    11    能力不足：某个 elewise 输入广播不到输出视图
#   data-movement             2    能力不足：局部 tile 收不成一段
#   --------------------------------------------------------------------
#   合计                     55
#
# 这四个桶与 2026-10-20-candidate-preparation-first-cause-69.txt 的 reg 侧逐格**完全一致**
# （那一轮的代码是探针式的，量完回退了，所以今天的表又回到无诊断）。本轮把那两处改动做成可留的
# 版本，并补了会红的 UT。
#
# **归属规则踩过一个坑，记在这里**：首因是「拒掉全部模板」的那一条，不是按判据顺序排在前面
# 的那一条。本轮第一版按 data-movement → elementwise-broadcast → queue-resources 报第一条非零
# 的，与 10-20 的逐格表差 3 格（indirect_load_both_transpose_simd_fallback /
# _nddma / indirect_load_user_embedding_sum_simd）。取这 3 格的完整诊断看：stage 有 2 个模板，
# queue-resources 把 2 个全拒了，另一条只拒了 1 个——只拒掉其中几个的判据不是卡点，换个模板它
# 就不成立。诊断现在直接报绑定判据（`all rejected by: ...; partially: ...`），UT
# `RejectionAttributionNamesThePredicateRejectingEveryTemplate` 钉住这个区别。
# 顺带：这行比原先短，活得过量具那个 150 字符截断——第一版就是因为 queue-resources 那一列被截
# 掉才把规则写错的。
#
# **还有一种情形：没有哪一条单独拒掉全部模板。** 两个模板各被不同的一条拒掉，覆盖是一个组合。
# `af-capability-probe` 的 T3 `f32 [1,8] -> [128,8]` 与 `[1,1,8] -> [4,4,8]` 就是这样
# （elementwise-broadcast 1 + queue-resources 1，各拒一个）。这时报不出单一首因，诊断如实说
# `no single predicate rejects all; counts: ...`，**不退回挑一条**——挑哪条都是把组合谎称成
# 单条。reg 侧 200 格表里没有这种行，但**mem 侧 38 格里有 2 格**（brc_inline_test_codegen 与
# inductor_topn_test_codegen，见下面的 mem 侧一节），所以这不是探针合成形状才有的情形。
# 这也订正了 2026-10-20 那份的 mem 分桶：它把 brc_inline 记成单条 queue-resources，实测是组合。
#
#===----------------------------------------------------------------------===#
# 为什么 att-tiling-key 那 16 格不标
#
# 它们**过了** plan selection，死在 `RunAttForCandidates` 之后的字段校验
# （`AttSchemaAdapter.cpp:130`）：ATT 生成的 tiling_func 引用 `graph0_tiling_key` 与
# `tiling_key`，而 `TilingFieldSchema` 发的是 `tiling_key`（flat）或
# `graph<N>_result<M>_tiling_key`（嵌套）——两侧拼法对不上第三种。
#
# **哪一侧对已经判了（2026-10-26）：legacy / ATT 对，MLIR 侧错。** 真源是
# `codegen/codegen_tiling_data.cpp` 的 `GetCommonTilingField(bool is_group, fused)`，它被调两次，
# 发的是两个不同的结构体：
#
#   外层 (ss1)  `GetCommonTilingField(false, fused)`，第 188 / 202 行
#               1 子图 && 1 plan && 1 stage -> `tiling_key`
#               否则                        -> `graph<i>_tiling_key`，**每个子图一个**（第 111 行）
#   组内 (ss2)  `GetCommonTilingField(true, {})`，第 565 行 -> 组局部的 `tiling_key`
#
# 对照 `mlir/common/tiling_schema/tiling_field_schema.cpp`，MLIR 侧有两处与它不符：
#
#   1. 外层键名多了 `result<M>`，而且是**按 plan 发**（`AppendPlanFields` 每个 plan 一个键）。
#      legacy 从来不发 `result<M>`，而且是按子图发。
#   2. **根本没有「组内」那个 `tiling_key`**。MLIR 的 `is_flat` 只实现了 legacy 条件里
#      1/1/1 那一支，`is_group` 那一支（组局部结构体）在 MLIR 这一侧没有对应物。
#
# 这正好解释诊断为什么同时少两个名字：ATT 引用的 `graph0_tiling_key` 来自外层、`tiling_key`
# 来自组内（`att/generator/final_tiling_repr_gen.cpp:86` 无条件发 `get_tiling_key()`，只在
# inductor + 单组时早退），两个都是 legacy 真有的字段，而 schema 两个都没发对。
#
# 所以修法在 MLIR 侧的 `tiling_field_schema.cpp`，**不是放开校验**。
#
# **已修（2026-10-26，提交 268011ba）**：外层键去掉 `result<M>` 并按子图发，每个嵌套 stage
# 结构体补一个组局部 `tiling_key`。实测 reg 硬失败 27 -> 11、mem 17 -> 6，两侧 takeover 不降、
# 0 格变差；mem 侧 7 格直接翻成 takeover（含 concat / topn 的图——又一次说明它们卡的不是算子
# 建模而是 tiling 字段拼法）。那 7 格里 4 格验过能生成 kernel 且数值过。
#
# **还剩一处分歧没动**：legacy 的嵌套字段是单层 `graph0_result0_g0_tiling_data`，而 MLIR 的
# path 是两层 `graph0_result0_tiling_data.g0_tiling_data`。`ValidateGeneratedFieldReferences`
# 只比叶子字段名、不比 path，所以它与那 27 格无关、也不会被这道校验发现；要不要对齐是独立一件。
#
# 这道校验本身是防静默错编的，不该放开；标成能力不足会把缺陷静默回落掉。所以标记只覆盖
# 39 格（26 + 11 + 2），**不是设计文档原先那条「把枚举失败统一标成能力不足」**。
#
#===----------------------------------------------------------------------===#
# 标记落点
#
# 能力不足的判据只有一个——`Diagnostic` 的 metadata（`support/CapabilityShortfall.h`），不是
# 诊断文本。plan selection 那一层没有 MLIR context，发不出带标记的诊断，所以那一层只透出一位
# 布尔 `unsupported`，由 `RunMlirCodegen` 发 `emitCapabilityShortfall(UnknownLoc) << diagnostic`。
# 判据因此仍然只有一个，没有第二套。
#
# 那一位跟着现有约定走（两个入口的 `diagnostic` 本来就是带默认值的尾参），现有 20 多个调用点
# 一个都没改。缺省 `false`，`SetUnsupported` 只置真不置假。
#
