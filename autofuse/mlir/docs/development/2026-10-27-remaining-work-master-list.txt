# step 3（Fma，2 格）的勘察结论（2026-10-28 核，省得下一轮重做）
#
#   供给：`AscendC::Fma`，标准调用、带 tmp，CANN 的 `adv_api/math/fma.h`：
#
#     Fma(dst, src0, src1, src2, sharedTmpBuffer, count)     <- tmp 在 count **之前**
#     Fma(dst, src0, src1, src2, count)                      <- 不带 tmp 的重载也有
#
#   `__NPU_ARCH__` 守卫 = {3510, 5102, 3003, 3113}，含 3510（reg_base 那一档用的那个），
#   所以这一位在我们的平台上不是空实现——与 `Hypot` 同一条，但要记着换平台会静默变空。
#
#   legacy 的域：`{DT_BF16, DT_FLOAT16, DT_FLOAT, DT_INT8, DT_INT16, DT_UINT8}`。
#   i8 不在 AFIR 的 7 位里，所以能注册的是 {f16, f32, bf16, i16, ui8}。
#
#   **卡点不在 dtype，而在操作数顺序**：三元那条现成 pattern 建的是
#
#     TargetOp(dst, condition, source0, source1, count, tmp)
#
#   ——`Where` / `Select` / `ClipByValue` 的形状，tmp 排在 count **之后**，而且第二个槽位
#   语义上是「条件」。Fma 的三个源是对称的，tmp 还在 count 之前。
#
#   这不需要新 pattern：**ODS 的 `arguments` 顺序是我们自己定的**，所以新建的
#   `FmaL2Op` 按 pattern 的顺序声明（dst, src0, src1, src2, calCount, sharedTmpBuffer），
#   由 emitter 打成 Fma 真实的顺序即可——`printOperation` 本来就是逐个取字段打的。
#   动笔前核一件事：`TernaryOperandTiles` 的 `condition` 只是「三个源里的第一个」这个
#   命名（出自 Select），还是真带条件语义。它要是只是命名，Fma 直接复用那条 pattern。
#
#   另外 `Fma` 要进 `kIsStockCall`（标准调用、无扩展头）——漏了整张注册表建不起来，
#   报 `failed to build the frozen AscendC implementation registry`，step 2 刚踩过。
#

# step 3 **写过一遍后整体退回**（2026-10-28 实测）。上面那些勘察结论都成立，下面是实测
# 补上的三件事，照这个顺序读。
#
#   1. `condition` **只是命名**，已核。证据有两条：`clip_by_value` 走的就是同一条
#      pattern 而 `conditionIsMask = false`（它的三个输入同 dtype），而
#      `Elementwise.td` 的 `AFIR_BufferizableTernaryHomoElementwiseOp` 上那段注释写着
#      「clip 的 `condition` / `input1` / `input2` 读作 x / min / max」；
#      `materializeOperandTiles` 对那三位只按下标排（`orderTilesForPlan` 收的是
#      `{condition, source0, source1}`），没有任何条件语义。
#      **所以不需要新 pattern**，`FmaL2Op` 按 pattern 的顺序声明 + emitter 打成
#      `Fma(dst, s0, s1, s2, tmp, count)` 这条路跑通了，产物逐字核过：
#
#        IR    ascendc.fma_l2 %arg3, %arg0, %arg1, %arg2, %0, %arg4
#        C++   AscendC::Fma(v4, v1, v2, v3, v5, v6);
#
#   2. **勘察漏了一件会改结论的事：legacy 在这个节点上会自己插 Cast。**
#      `FmaAscIrCodegenImplV2::GetConversionDtype` 的对表是
#      `{bf16->f32, i8->f16, i16->f32, ui8->f16}`，由 `optimize/graph_completeness/`
#      的 `DtypeConsistency` 在调度之前施加。也就是说 legacy **从不发
#      `Fma<bfloat16>`**，`REG_ASC_IR(Fma)` 那六位里真正发到 `Fma` 的只有 f16 / f32。
#      注册 {f16,f32,bf16,i16,ui8} 不算错（判据是「不得比 legacy 窄」，对账的是
#      `REG_ASC_IR`），但**它不是接不接得下来的那根轴**——见下一条。
#
#   3. **真卡点：`abs_fma_bf16` 从干净回落变成硬失败，卡在 `afir.store` 的两端 dtype。**
#      实测（远端 AF_MLIR_0814，量具与 s2a 同一台，自检 WARNING 0 条、没打出标签的行 0）：
#
#        takeover      81 -> 82    （abs_fma_test        fallback -> takeover）
#        hard-failure  11 -> 12    （abs_fma_bf16_test   fallback -> **hard-failure**）
#        200 行里只有这 2 行变，198 行逐字未变。
#
#      诊断：`error: 'afir.store' op transfer source and destination must have the same
#      element type`。**这与 2b 是同一道闸门**，而且这一格的矛盾更明显——legacy 自己
#      调度出来的签名就是对不上的（`AutoFuseAfterOptimize` 的 dump）：
#
#        func @abs_fma_bf16_test_0_B0Y0_S0G0C0(%data0: bf16[s0], ..., %output: f32[s0])
#          %7 = ascir.ops.Fma(%3, %4, %6)      -> vector<z0t_sizexf32>
#          %8 = ascir.ops.Cast(%7)             -> vector<z0t_sizexbf16>   # fma_cast_to_store
#          %9 = ascir.ops.Store(%8)            -> output: %output         <- %output 是 f32
#
#      `DtypeConsistency` 把 Fma 抬到 f32、又在 store 前插了一条回到 bf16 的 Cast，
#      **但函数签名上的 GM 侧仍是 f32**。store 的两端于是 bf16 / f32。
#
#      **这根轴上没有 dtype 旋钮可拧**：把注册集合收窄到 {f16,f32} 也拦不住它——那条
#      `afir.fma` 在这张图里本来就是 f32，硬失败发生在 bridge 建 `afir.store` 时的
#      verifier 上，比 implementation 选择更早。唯一的闸门是 bridge 收不收 `Fma`
#      这个**节点类型**，而那是全有或全无的。
#
#   所以 step 3 的 2 格拆成：1 格（`abs_fma_test`）接得下来、1 格（`abs_fma_bf16_test`）
#   与 2b 的两格、以及 s2a 表里那 9 格带同一条诊断的硬失败共用一个前置。为了 1 格而引入
#   1 格硬失败（legacy ST 那一档会真红，shortfall=no）不划算，所以**整个 step 3 退回**，
#   代码一行没留。
#
#   **前置变大了，优先级也该变**：给「两端 dtype 不同」的 store 定语义（capability 层
#   干净拒收，或显式建模成一次 reinterpret）现在挡着 **2b 的 2 格 + Fma 的 1 格**，
#   并且是 s2a 表里 11 格硬失败中 9 格的首因。它不再是「独立一件小活」，而是这一族里
#   收益最大的那一件。动它之前要先定判据：按字节宽度放开会把硬失败换成静默算错，更坏。
#

# 订正：上面「两端 dtype 不同但字节宽度相同」那半前置**根本不需要存在**——是

# 订正：四个 ToInt **不是同形**，要拆两组（2026-10-28 核 legacy 注册）
#
#   之前把 Ceil2Int / FloorToInt / RoundToInt / TruncToInt 排成「四格一组、一个新机制」，
#   不对。四个的 ApiCall 名字四个都不同（CastV2ApiCall / FloorToIntApiCall /
#   RoundToIntApiCall / TruncToIntApiCall），照一个抄会全答错。按 REG_ASC_IR 逐个核：
#
#     Ceil2Int    输入 {f32,f16,bf16} -> 输出**恒 i32**   Ceil2IntExtend + cast_reg_base.h
#     FloorToInt  输入 {bf16,f16,f32} -> 输出**恒 i32**   标准调用 FloorToInt
#       这两个的输出 dtype 单一，像谓词族的 Uint8 规则，加一条 Int32 规则就够 —— 便宜。
#
#     RoundToInt  (输入,输出) **逐对对表**   RoundToIntApiCall + tmp
#     TruncToInt  (输入,输出) **逐对对表**   TruncToIntApiCall + tmp
#       两个的对表都是 f32->i64 / f32->i32 / f32->i16 / f16->i16 / f16->i32 /
#       f16->i8 / f16->ui8 / bf16->i32。必须复用 afir.cast 那套
#       `ResultElementRule::CastPair`，而且 i64 / i8 / ui8 不在 AFIR 供给表里，
#       只能接可建模的那个子集 —— 要先定子集再动笔。
#
#   所以原 step 2 拆成 2a（Ceil2Int + FloorToInt，2 格）与 2b（RoundToInt + TruncToInt，
#   2 格）。
#
#   **2a 已接（2026-10-28），2b 实测卡在别处、已退回（代码写过一遍，结论如下）**：
#
#   2b 的卡点**不是那张对表**。对表量清楚了：那 8 对（f32->i64/i32/i16、f16->i16/i32/i8/ui8、
#   bf16->i32）全在 `getRegBasedCastPairs()` 里，但 reg 的 cast 表还多 `f32->i8` 与
#   `f16->i64`，所以不能复用 `CastPair`（会比 legacy 宽，宽就是注册表里的假话），要另起一张
#   8 对表。这部分做完了、UT 也过了。
#
#   真卡点是 **`afir.store` 的「两端 dtype 必须相同」**。legacy 自己调度出来的图就是矛盾的：
#
#     func @round_to_int_float_to_int32_test_0_B0Y2_S0G0C0(%data: f32[s0,s1], %output: f32[s0,s1])
#       %2 = ascir.ops.RoundToInt(%1) -> vector<z0z1t_sizexi32>
#       %3 = ascir.ops.Store(%2) -> output: %output        <- %output 是 f32
#
#   存的是 i32、GM 那一侧是 f32。那个 f32 是 legacy 在 MLIR 跑起来之前定的（函数签名出自
#   legacy 的调度结果，`share_graph.cc` 里那张图自己把 `round_to_int.y` 和 `store.y` 都设成
#   了 DT_INT32，是外层 GE 图的 netoutput 仍是 f32）。legacy 的 store 按字节搬、i32 与 f32
#   都是 4 字节所以它「能跑」；MLIR 的 `afir.store` 有那条不变量，于是**硬失败**。
#
#   接 2b 的结果实测是 takeover 79 -> 81 而 hard-failure 11 -> 13：2a 那两格干净翻过来，
#   2b 那两格从干净回落变成硬失败。**与 uint8 那一族是同一道闸门**（见
#   `uint8 卡在 afir.store 不能换 dtype`），「放开 bridge 白名单会把它从回落翻成硬失败」。
#
#   不为这两格放开 store 那条闸门：那会把一个硬失败换成按字节重解释的静默错值，而且影响
#   所有图。接 2b 的前置是先给 store 这种「两端 dtype 不同但字节宽度相同」的情形定出
#   语义（要么在 capability 层干净拒收、要么显式建模成一次 reinterpret），那是独立一件活。
#

# 阻塞项：aarch64 上 `libcodegen.so` 已到链接上限（2026-10-27 实测，**所有补 op 的前置**）
#
#   症状：legacy ST 档链 `autofuse/tests/libcodegen.so` 时
#         `relocation truncated to fit: R_AARCH64_CALL26 against symbol
#          __aarch64_ldadd4_acq_rel`（libgcc.a 里），整档编不过，于是接管表量不出来
#         （200 行全落 `no-hook-call`，量具自检会报「没打出标签的行: 200」）。
#
#   量出来的数（远端 AF_MLIR_0814，aarch64）：
#
#     R_AARCH64_CALL26 的跳转范围        ±128 MiB = 134,217,728 B
#     ff7f72dd 干净树   .text            131,625,104 B = 125.53 MiB  (98.1%，余 2.59 MB)
#     落第 8 批后       .text            132,104,064 B = 125.98 MiB  (98.4%，余 2.11 MB)
#     第 8 批代价                        478,960 B / 4 个 op 类 ≈ 117 KB 每个 op 类
#                                        （一个 op = AFIR 1 类 + AscendC 1 类）
#     libcodegen.so 总大小               228.7 MB，链进去 50 个 LLVM 静态归档
#     链接选项                           无 --long-plt、无 -mcmodel、无 --gc-sections
#
#   **「余 2.11 MB」是上界而不是预算**：这条重定位限的是调用方与被调方的**距离**，
#   不是 .text 总字节数，所以溢出会在总量到 128 MiB 之前就发生。实测第 9 批那 16 个
#   op 类（外加 8 次 pattern 实例化）就溢出了，而按 117 KB 估只有 1.87 MB < 2.11 MB
#   ——照字节数做预算会估乐观。
#
#   x86_64 不受影响（相对调用 ±2GB），本地全套件照常绿。**所以这面墙只在 aarch64 上，
#   而接管表只能在 aarch64 上量**，于是它同时挡着验收。
#
#   没解开之前：第 9 批（多项式族八个）代码已写好并在 x86_64 上验过，挂起不落
#   （补丁留在 session 的 scratchpad）。后面 step 2–6 约 16 个 op = 32 个 op 类，
#   一步都过不去。
#
#   **已解（2026-10-27）**，三个变体逐个实测：
#
#     A 基线                        .text 132,104,064 B = 126.0 MiB   余  2.11 MB
#     B -ffunction-sections -fdata-sections + -Wl,--gc-sections
#                                   .text 131,283,792 B = 125.2 MiB   余  2.93 MB  省 0.78 MiB
#     C B + -Wl,--exclude-libs,ALL  .text 105,849,696 B = 100.9 MiB   余 28.37 MB  省 25 MiB
#
#   **B 是 C 的前置，不是「C 的弱化版」**：`libcodegen.so` 默认可见性下每个全局函数都进
#   `.dynsym`、都是 GC 的根，所以单加 `--gc-sections` 基本无事可做（省下的 0.78 MiB 大致
#   是我们自己那部分代码）。`--exclude-libs,ALL` 把静态归档的符号变成本地的之后，那 50 个
#   LLVM 归档里用不上的函数才真的成了垃圾；反过来没有 `-ffunction-sections`，exclude-libs
#   也只能按整个 .o 丢。两个要一起加。
#
#   验收判据**不是「链接过了」也不是「测试都 Passed」，而是接管表逐格不变**——链接选项
#   不该改变任何一格的结论。实测 200 格与 `c0f6719c` 那份逐字相同（0 行差异）。
#   顺带：`--exclude-libs,ALL` 会把 `graph_af` / `ascir` / `att` 这些非 LLVM 归档的符号也
#   隐掉，所以「200 个 ctest 还跑得起来」这一条是必须验的，不能只看 .text 掉了多少。
#
#   选项只加在 `ENABLE_AUTOFUSE_MLIR` 那一档：不链 MLIR 的 legacy 档离上限还远。
#   没用上的两条备选（收窄 LLVM 归档清单 / 拆 `libcodegen.so`）留着——余量 28 MB 按第 8 批
#   量出的 117 KB 每个 op 类算够两百多个，现在不必动。

# 下一步计划（2026-10-28 收尾，接管表当前 95，供后续 session 直接取用）
#
# 下面五项排了个大致的「接个算子就行」到「要先设计」的顺序，互相独立，谁先做都不挡别人。
# 每项给了现成的勘察事实（legacy 供给、dtype 域、header、卡点），不用重新核。

#   1. RoundToInt / TruncToInt（2b，2 格）—— **纯补注册，样板已经干净**

#      tmp，(输入,输出) 逐对对表（不是 `Same`/`Int32` 那种统一规则），8 对：
#      f32->i64/i32/i16、f16->i16/i32/i8/ui8、bf16->i32。**不能复用 `afir.cast` 的

#      legacy 的 `SignBitAscIrCodegenImplV2`：`GetApiCallName` = `UnaryApiTmpCall`，
#      `GetApiName` = `SignBitExtend`，`LoadApiHeaderFiles` = `{"signbit_reg_base.h"}`，
#      `CalcTmpBufSize` 走 `CalcVoidTmpSizeV2`（尺寸 0 但形参在，与 `afir.hypot` 同一种
#      情况）。输入 T = {float, int32}，输出 U = {uint8, bool}——与谓词族
#      （`Uint8Logical`/`AFIR_PredicateElementwiseOp`）同一个「输入输出 dtype 不同」的
#      形状，但输入域不是纯浮点（带 int32），要单独核 ODS 的 `resultRule` 怎么写。
#      只有 reg 一侧。先确认 `api_regbase/signbit.h`（或类似文件名）里的包装签名。
#
#   3. Frexp（1 格）—— **双输出**，机制与前两项不同
#      legacy 的 `REG_ASC_IR(Frexp)` 有两个输出（`mantissa`、`exponent`，`T`=float、
#      `U`=int32）。AFIR 今天唯一的多输出 op 是 `afir.vector_func`（见
#      `appendBufferNodeAttrs` 里「多输出的算子必须显式传全部」那段注释，
#      `DescriptorCountMismatch` 是它的硬失败信号）。接 `Frexp` 前先确定要不要让
#      elementwise 这条路也支持多输出 destination，还是给它单开一条路——这是一个要先
#      想清楚的设计点，不是照抄就能接的单点算子。
#
#   4. scalar_cast_add 硬失败 —— **`afir.cast` 不收标量操作数**
#      `ScalarCastAddFusedGraph(3, af::DT_FLOAT16, af::DT_FLOAT)`

#      Cast 的输入直接是一个 `Scalar` 节点，没有 Load 成 tile。诊断
#      `'afir.cast' op operand #0 must be Tensor or MemRef of ...`
#      ——`AFIR_CastElementTypes`（`Cast.td:72`）本身收 F16，不是 dtype 域的问题，是
#      `afir.cast` 的 ODS 操作数类型要求「必须是 Tensor/MemRef」，不接受裸标量，
#      与其余二元 op 的 `scalarOperand` 旋钮不是一回事（Cast 是一元）。要不要给
#      `afir.cast` 开一个标量输入的变体，还是把 bridge 侧的 Scalar 预先物化成一个单元素

#      `"inf"`。`buildTypedConstant`（`AfirBuilder.cpp:966`）故意挡掉非数字开头的字面量

#      `std::numeric_limits<float>::infinity()`）**。动笔前先跑一遍 legacy 单独编译这张
#      图，看它是不是真的也编不过；如果编得过，说明那条挡字面量的判据漏了一种合法写法，
#      要去 legacy 的字面量渲染那一层抄规则，不能直接放开。

#   以上五项与 [[store-dtype-mismatch-was-fixture-bug]] 那类「先去查样板」的纪律无关

#   I.1  广播目的张量 UB 缓冲分配过小，大尺寸广播在 counter mode 下 Copy 越界崩溃
#        现象：`load_broadcast_abs_store` 注册 `INPUT_SHAPES "[2048, 1]"`、
#        `OUTPUT_SHAPE "[2048, 2048]"`（f32，两根轴都大到要各自切 tile）后，CPU 仿真**全部
#        40 个核心真实崩溃**，不是静默产生错误结果：
#
#          [ERROR]Failed to check dstLocal size in Copy when in counter mode, tensor size
#          needs to be at least 254208 bytes, while current tensor size is only 90112 bytes.
#          [ERROR]...Failed to pass Copy mask count mode check.
#
#        数值对照 4,194,304 个元素里 4,192,256 个不对（含下标 0），是设备侧中止导致输出缓冲
#        停在初值，不是算法算错——报错是真失败，不是 H.1 那种「声称接管却静默错」。
#
#        **2026-11-11 深挖结论：我们自己的缓冲分配是对的，卡点在 CANN 闭源库内部，查不下去**。
#        实测打点（临时在生成的 `kernel.cpp` 里插 `printf`，只改 build 产物不改源码）拿到真实
#        运行值：`dst_m=11`、目的队列缓冲 `v10=90112` 字节（即 22528 个 f32，刚好等于
#        `11 * 2048`——与「11 行、每行 2048 列」的逐元素需求**完全吃满，不多不少**）。按
#        CANN 头文件里能读到的算法（`broadcast_v220_impl.h` 的 `TwoDimBroadCastLastDim` →
#        `numBlocks(2048) * sizeof(f32) % ONE_BLK_SIZE(32) == 0` 为真，走 `Align` 分支 →
#        `TwoDimBroadCastLastDimAlign220`，`firstDim=11 < MAX_REPEAT_TIMES(255)`，只发一次
#        `Copy<T,false>(..., repeatTime=11, dstRepStride=256 blocks)`），手算这次 `Copy`
#        该写的总字节数同样是 `11*2048*4=90112`，与我们给的缓冲吃满、不短。但报错的那个
#        `Copy` 自带的 `CheckFuncCopy`→`CheckFuncCopyImpl` 校验要的是 254208 字节（63552
#        个 f32），比按源码算出来的「应该够」多了约 2.82 倍——**这条校验的实现不在任何头文件
#        里，是编译进 `libcpudebug.so` / `libtikcpp_debug.so` 的符号（`nm -D` 能看到
#        `CheckFuncCopyImpl`，但没有对应的 `.cpp` 源码可读），没有反汇编或官方文档做不到按
#        公式对账**。已排除的可能：不是 tmp_buf 太小报错（那条断言文本不同，且 tmp_buf=8192
#        字节按 `GetAlignLoopNumbers` 算出的 `oneRepeatSize=256` 本来就比 `firstDim=11` 大，
#        不会触发分块）；不是我们的队列缓冲 `size_bytes_expr` 算少了（逐元素对平，吃满
#        不短）。
#        **复现**：在 `test/e2e/cpu/cases/load_broadcast_abs_store/CMakeLists.txt` 临时加
#        `add_mlir_e2e_cpu_case(load_broadcast_abs_store_2048x2048_probe OUTPUT_SHAPE
#        "[2048, 2048]" INPUT_SHAPES "[2048, 1]")`，重配 cmake 后
#        `cmake --build build --target check-e2e-cpu-load_broadcast_abs_store_2048x2048_probe`。
#        要复核实测值，在生成的 `kernel.cpp` 里 `Broadcast(v106, v102, ...)` 调用前插一行
#        `printf` 打印 `v89`/`v10`/`v34.GetSize()` 等变量，手动重编那一个 `.o`（不要走
